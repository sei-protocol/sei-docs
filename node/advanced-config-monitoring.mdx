## Optimizing system configuration

The number of possible setups is virtually unlimited, so this document cannot cover them all. Even similar builds and configurations can behave differently because of external factors. Your results may vary.

Use these general guidelines as a starting point. Be cautious and make incremental changes. Test and observe each change before you move forward.

Always focus on only one specific area at a time. Do not change the memory, storage, and CPU configurations all at once. Otherwise, it becomes nearly impossible to diagnose problems.

### Memory management

These settings in `/etc/sysctl.conf` can optimize memory usage and disk I/O patterns:

```bash
# Minimize swapping
vm.swappiness = 1

# Control disk write behavior
vm.dirty_background_ratio = 3
vm.dirty_ratio = 10
vm.dirty_expire_centisecs = 300
vm.dirty_writeback_centisecs = 100
```

To apply the changes, run `sudo sysctl -p`.

### Network stack

These settings in `/etc/sysctl.conf` may improve network performance:

```bash
# Increase connection handling capacity
net.core.somaxconn = 32768
net.core.netdev_max_backlog = 32768
net.ipv4.tcp_max_syn_backlog = 16384

# Optimize buffer sizes
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 87380 16777216
```

### Storage configuration

For NVMe drives, optimize I/O scheduling:

Storage optimization commands

```bash
# Set IO scheduler
echo "none" > /sys/block/nvme0n1/queue/scheduler

# Set read-ahead buffer
blockdev --setra 4096 /dev/nvme0n1

# Set IO priority in systemd service
sudo tee -a /etc/systemd/system/seid.service << EOF
[Service]
IOSchedulingClass=realtime
IOSchedulingPriority=2
EOF

# Configure disk mount options
sudo tee -a /etc/fstab << EOF
/dev/nvme0n1p1 /data ext4 defaults,noatime,nosuid,nodev,noexec,commit=60 0 0
EOF
```

## Infrastructure monitoring

Monitoring is one of the most critical components of network infrastructure. This page covers monitoring, performance tuning, and alerting configuration for Cosmos SDK and Tendermint nodes.

### Prometheus setup

First, install Prometheus:



<Warning>
The application Prometheus sink is off by default. A node whose `app.toml` is generated by v6.8.0 gets `prometheus-retention-time = 0` under `[telemetry]`, which leaves the sink uncreated even though `telemetry.enabled` stays `true`. `GET /metrics?format=prometheus` on the app API server (:1317) then returns `prometheus metrics are not enabled`, and `seid` exports no application Prometheus series. If you scrape application metrics, set a positive `[telemetry] prometheus-retention-time` in `app.toml` (the previous default was `7200`) before generating a new configuration file. Nodes that already have `prometheus-retention-time` written in `app.toml` are unaffected (#4032).

```toml
[telemetry]
prometheus-retention-time = 7200
```
</Warning>

<Accordion title="Create alert rules configuration">

```yaml
groups:
  - name: validator_alerts
    rules:
      - alert: NodeDown
        expr: up == 0
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: 'Node {{ $labels.instance }} down'

      - alert: BlockProductionSlow
        expr: rate(tendermint_consensus_height[5m]) < 0.1
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: 'Block production is slow on {{ $labels.instance }}'
      - alert: ValidatorMissedBlocks
        expr: increase(tendermint_consensus_validator_missed_blocks[1h]) > 0
        labels:
          severity: critical
        annotations:
          summary: 'Validator missing blocks'

      - alert: ValidatorJailed
        expr: tendermint_consensus_validator_status == 0
        labels:
          severity: critical
        annotations:
          summary: 'Validator has been jailed'

      - alert: ConsensusStalled
        expr: tendermint_consensus_height_status == 0
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: 'Consensus has stalled'
```

</Accordion>

```sh
#!/bin/bash

MONIKER="$1"
API_URL="http://localhost:1317/cosmos/staking/v1beta1/validators?pagination.limit=500"

echo "Querying validators from $API_URL..."

VALIDATOR_DATA=$(curl -s "$API_URL" | jq -c --arg MONIKER "$MONIKER" '.validators[] | select(.description.moniker == $MONIKER)')

if [[ -z "$VALIDATOR_DATA" ]]; then
    echo "❌ No validator found with moniker: $MONIKER"
    exit 1

echo "Validator details:"
echo "$VALIDATOR_DATA" | jq '.'
```

## Backup management

<Accordion title="Complete automated backup script">

```bash
#!/bin/bash
BACKUP_DIR="/backup/sei"
DATE=$(date +%Y%m%d)
NODE_HOME="/root/.sei"

# Create backup directory
mkdir -p $BACKUP_DIR

# Stop service
systemctl stop seid

# Backup configuration
tar czf $BACKUP_DIR/sei-config-$DATE.tar.gz $NODE_HOME/config

# Backup data directory
tar czf $BACKUP_DIR/sei-data-$DATE.tar.gz $NODE_HOME/data

# Backup key files
tar czf $BACKUP_DIR/sei-keys-$DATE.tar.gz $NODE_HOME/keyring-file

# Start service
systemctl start seid

# Remove backups older than 7 days
find $BACKUP_DIR -type f -mtime +7 -name '*.tar.gz' -delete

# Log backup completion
echo "Backup completed successfully on $(date)" >> $BACKUP_DIR/backup.log
```

## Seed node Prometheus metrics

Since v6.7.0, seed nodes serve Prometheus metrics like other nodes. A seed serves no RPC, so its p2p metrics, such as `tendermint_p2p_peers`, are the only way to watch it. Enable them in the `[instrumentation]` section of `config.toml`:



Alongside `tendermint_p2p_peers`, the node exports the `tendermint_p2p_known_addresses` gauge, which reports the number of distinct peers with a known address: connected peers plus those learned via PEX. Like the peers gauge, it is published at router construction so the series exists before the node starts, and it is refreshed periodically thereafter.


```toml
[instrumentation]
prometheus = true
prometheus-listen-addr = ":26660"
```

<Warning>
If a seed node cannot open the Prometheus listener, the seed fails to start. For example, the port can be in use, or the address can be invalid. A full node logs the error and continues to run.
</Warning>

### Metrics server limits

The metrics server uses a 10s read header timeout, a 10s read timeout, a 30s write timeout, and a 60s idle timeout.

`max-open-connections` under `[instrumentation]` is not a connection limit. It caps the number of scrapes that the server handles at the same time. Requests over the cap get HTTP `503`. The server does not queue them. A slow scraper holds its slot until it finishes or reaches the write timeout. `0` means no limit. The default is `3`. Set the value higher than the number of scrapers that can overlap, such as an HA Prometheus pair, probes, and manual `curl` requests.

## `chain_id` label on metrics

Since v6.7.0, the node adds a `chain_id` label to every metric that it exports. This includes the Tendermint Prometheus metrics, the Cosmos SDK telemetry, and the OpenTelemetry metrics (`evmrpc_*`, `flatkv_*`, `litt_*`, and `pebble_*`). If you already set `chain_id` in `global-labels` under `[telemetry]`, the Cosmos SDK telemetry keeps your value.

Update PromQL that aggregates across series, such as `sum(...) without (...)` or `by (...)`, to account for the new label. To scope a query to one chain, add a `chain_id` match.

## EVM RPC OpenTelemetry metrics

The EVM RPC layer emits OpenTelemetry metrics through the process-wide `MeterProvider` (for example, a Prometheus exporter). It emits these metrics in parallel with the legacy `sei_*` metrics, so you can migrate dashboards incrementally.

### Available EVM RPC metrics

| Metric | Type | Description |
| --- | --- | --- |
| `evmrpc_request_latency_seconds` | Histogram | EVM RPC request latency in seconds. |
| `evmrpc_websocket_connects_total` | Counter | Number of new WebSocket connections. |
| `evmrpc_websocket_connections` | Gauge (Int64UpDownCounter) | Number of currently connected WebSocket clients. Incremented on connect and decremented on disconnect. |
| `evmrpc_redirected_requests_total` | Counter | Number of EVM RPC requests forwarded to another validator. Labeled by `endpoint` and `connection`. |
| `evmrpc_historical_debug_trace_attempts_total` | Counter | Number of `debug_trace*` requests that target historical blocks beyond the configured max block lookback. Labeled by `endpoint` and `connection`. |
| `evmrpc_requests_rejected_total` | Counter | Number of JSON-RPC requests that admission control rejected. Labeled by `protocol` (`http` or `ws`) and `reason`. For HTTP, `reason` is `oversize` (larger than `max_request_body_bytes`, HTTP 413), `budget_midread` (the `max_concurrent_request_bytes` budget ran out, HTTP 429), `slow_body`, `rate_limited`, `unparseable`, or `read_error`. For WebSocket, `reason` is `oversize` (close code `1009`) or `busy` (no budget within `ws_admission_timeout`, JSON-RPC error `-32005`). See [Frame size and concurrency limits](/evm/evm-parity/websocket#frame-size-and-concurrency-limits). |



<Warning>
Rate limiting is now enabled by default across EVM RPC, gRPC, and Tendermint RPC (#4299). A newly generated `app.toml` sets EVM `rate_limiting_enabled = true`, a generated `config.toml` enables Tendermint RPC rate limiting, and gRPC `rate-limiting-enabled` now defaults to `true`. As a result, operators will see HTTP 429 (`too many requests`) rejections by default when clients exceed the per-IP limits, reflected in `evmrpc_requests_rejected_total` with `reason` `rate_limited`. The default EVM `batch_request_limit` also dropped from `1000` to `100`, and the default EVM per-IP burst (`ip_rate_limit_burst`) is now `200`.

When `rate_limiting_enabled` is inherited (not explicitly set in `app.toml`) and a configured `ip_rate_limit_burst` is below `batch_request_limit`, the node now raises the burst to the batch limit and logs a warning instead of failing to start. If you set `rate_limiting_enabled` explicitly, a burst below the batch limit is still rejected at startup; set `ip_rate_limit_burst >= batch_request_limit` in that case. To restore the previous behavior, set `rate_limiting_enabled = false` under `[evm]`, `rate-limiting-enabled = false` under `[grpc]`, and the corresponding Tendermint RPC switch in `config.toml`.
</Warning>



The EVM RPC per-IP rate limit is configured by `ip_rate_limit_rps` and `ip_rate_limit_burst` in the `[evm]` section of `app.toml`. These two fields can be overridden at startup by the `EVM_IP_RATE_LIMIT_RPS` and `EVM_IP_RATE_LIMIT_BURST` environment variables. When an environment variable is set, it takes precedence over the corresponding `app.toml` field; when it is unset, the `app.toml` value applies. This override is primarily useful for test and CI setups that drive a node from a single IP and would otherwise hit the default per-IP limits.

```toml
[evm]
ip_rate_limit_rps = 300
ip_rate_limit_burst = 1500
```

```bash
# Override the app.toml values at startup
export EVM_IP_RATE_LIMIT_RPS=300
export EVM_IP_RATE_LIMIT_BURST=1500
```

The node also rejects JSON-RPC batches larger than `evm.batch_request_limit` (default `100`). Clients that submit batched requests must keep each batch at or below this limit.



## Block filter polling

The `max_block_filter_hashes` field in the `[evm]` section of `app.toml` governs how an `eth_newBlockFilter` filter handles block hashes. Its meaning depends on whether the node runs with a block header notifier (Autobahn):

- Under Autobahn, the filter collects block hashes from the notifier, and a filter that holds more than this many unpolled hashes is invalidated and removed.
- Otherwise there is no notifier, and the filter polls the CometBFT block store from a cursor that starts at the block after the head at filter creation, so no poll returns a block from before the filter existed. In this mode one `eth_getFilterChanges` poll covers at most `max_block_filter_hashes` block heights and returns their hashes oldest-first; later polls cover the rest. When pruning passes the cursor, the poll fails with a `-32000` error naming the pruned blocks, and the filter resumes from the earliest available block.

```toml
[evm]
max_block_filter_hashes = 10000
```

<Note>
`eth_getFilterLogs` rejects a block filter as not existing (`filter does not exist`), matching geth behavior.
</Note>

When rate limiting rejects a JSON-RPC batch POST with HTTP 429 (`too many requests`), the rejection response now mirrors the shape of the request. A valid batch within the request batch size limit returns a JSON array of error objects, one per non-notification request, each preserving its request ID. A batch made up only of notifications returns an empty body, just as it would when served. An oversized batch (above the request batch size limit) or a malformed batch still returns a single JSON-RPC error object. Single (non-batch) requests continue to return a single error object preserving the request ID.

The `evmrpc_request_latency_seconds` histogram carries these labels:

| Label | Description |
| --- | --- |
| `endpoint` | The RPC method that the node serves (for example, `eth_getBalance`). |
| `connection` | The connection type that serves the request (for example, `http` or `websocket`). |
| `success` | Boolean that indicates whether the request succeeded. |
| `error_class` | A low-cardinality classification of the failure. An empty string means success. Possible values include `panic`, `execution_reverted`, `evm_not_supported`, `sei_legacy_disabled`, `association_missing`, `jsonrpc_error`, and `unknown`. |
| `jsonrpc_code` | A low-cardinality bucket for the JSON-RPC error code: `spec` (predefined range `-32700..-32600`), `server` (server-defined range `-32099..-32000`), or `other`. An empty string means no code (success or an untyped error). |

### Migrating from legacy EVM RPC metrics

These legacy `sei_*` metrics remain available today but are deprecated. They are scheduled for removal after dashboards migrate to the `evmrpc_*` OpenTelemetry metrics:

| Legacy metric | Replacement |
| --- | --- |
| `sei_rpc_request_latency_ms` | `evmrpc_request_latency_seconds` |
| `sei_websocket_connect` | `evmrpc_websocket_connects_total` |

### EVM RPC per-method deadlines

EVM JSON-RPC methods are bounded by a per-method deadline over both HTTP and WebSocket (#4299). A method that exceeds its deadline returns a `context deadline exceeded` error. When this happens the node increments the OpenTelemetry counter `rpc_deadline_exceeded_total`, labeled by `plane` (for example, `evm`) and `method_namespace` (for example, `eth`), so you can alert on methods that run past their deadline.

| Metric | Type | Description |
| --- | --- | --- |
| `rpc_deadline_exceeded_total` | Counter | Number of EVM JSON-RPC requests that exceeded their configured deadline. Labeled by `plane` and `method_namespace`. |

Configure the deadlines in the `[evm]` section of `app.toml`:

| Config key | Default | Description |
| --- | --- | --- |
| `rpc_default_timeout` | `30s` | Deadline applied (on both HTTP and WebSocket) to any RPC method with no entry in `rpc_method_timeouts`, such as `eth_getBalance` or `eth_getBlockByNumber`. Set to `0` to disable (no deadline applied). HTTP requests are also bounded by `write_timeout`; raise it to permit a longer method timeout over HTTP. |
| `rpc_method_timeouts` | `["eth_estimateGasAfterCalls=5m"]` | List of `"method=duration"` strings that override `rpc_default_timeout` for individual methods. A method name ending in `*` (for example, `"debug_trace*=0"`) matches every method with that prefix; the longest matching prefix wins. A duration of `0` means no deadline is applied by this mechanism. |

```toml
[evm]
rpc_default_timeout = "30s"
rpc_method_timeouts = ["eth_estimateGasAfterCalls=5m"]
```

The simulation methods `eth_call`, `eth_estimateGas`, and `eth_createAccessList` use the configured `SimulationEVMTimeout` as their dispatch deadline. A wildcard entry in `rpc_method_timeouts` cannot change the timeout for `eth_call`, `eth_estimateGas`, `eth_createAccessList`, `eth_sendRawTransaction`, `eth_sendTransaction`, `eth_getTransactionCount`, or `debug_trace*` methods, because each already has its own exact or prefix entry that takes precedence. To change one of these, name it exactly, for example `"eth_call=1s"`.

### Available FlatKV metrics

| --- | --- | --- |
| `flatkv_open_latency` | Histogram | Time taken to open the FlatKV store (seconds). |
| `flatkv_apply_changesets_latency` | Histogram | Time taken to apply changesets to FlatKV (seconds). |
| `flatkv_commit_latency` | Histogram | Time taken to commit FlatKV changes (seconds). |
| `flatkv_commit_batch_latency` | Histogram | Time taken to commit a FlatKV data DB batch (seconds). |
| `flatkv_batch_read_old_values_latency` | Histogram | Time taken to batch read old FlatKV values (seconds). |

### Pebble internal metrics

FlatKV turns on Pebble's internal metrics for each data DB by default. The node does not apply an `enable-pebble-metrics` key from `app.toml`.



### FlatKV snapshot retention

FlatKV publishes periodic checkpoints and keeps a number of old ones besides the latest so that composite reads and rollbacks can reach a version both backends still hold. Configure retention in the `[state-commit.flatkv]` section of `app.toml`:

| Config key | Default | Description |
| --- | --- | --- |
| `snapshot-keep-recent` | `10` | Number of old checkpoints to keep besides the latest. `0` keeps only the current checkpoint (no old ones). Ignored entirely when external pruning is set. |

```toml
[state-commit.flatkv]
snapshot-keep-recent = 10
```

The default retention is `10` old checkpoints (#4322). A composite read needs a version that both FlatKV and memIAVL still hold. At mainnet state size memIAVL publishes a snapshot only about every 50,000 blocks, so FlatKV must reach back further than that: ten old checkpoints at FlatKV's snapshot interval reach roughly 100,000 blocks. Because a checkpoint hardlinks its SSTs, each one costs only what compaction has obsoleted since, about 290 MiB at mainnet state size.

FlatKV's `snapshot-keep-recent` is no longer derived from memIAVL's `sc-keep-recent`; it uses its own configured or default value. Only FlatKV's snapshot interval follows memIAVL's effective snapshot interval.

## Subspace query metrics

`/store/*/subspace` ABCI queries are served only from the state store (SS). On a node with SS disabled, every `/subspace` query is now rejected with an `ErrNotSupported` error (`subspace queries require the state store`) before it takes a concurrency permit. A scan that would exceed the configured pair or byte caps fails with `subspace result exceeds limit`, empty prefixes are rejected, and queries that exceed the concurrency limit are rejected with `subspace query busy`. The concurrency limit bounds concurrent `/subspace` queries; because only nodes with SS enabled serve `/subspace`, it applies only to those nodes. Indexers and tooling that issue wide `/subspace` queries must narrow their prefixes, shard by sub-prefix, or raise the caps in `app.toml` (#4009).

| Metric | Type | Description |
| --- | --- | --- |
| `subspace_query_rejected` | Counter | Number of rejected `/subspace` ABCI queries. Labeled by `reason`: `semaphore` (the concurrency limit was exceeded), `cap_exceeded` (the scan hit the pair or byte cap), or `ss_disabled` (the query was rejected because the state store is disabled). |

Tune the caps in the `[state-commit]` section of `app.toml`. Values `<= 0` resolve to the defaults; there is no unlimited setting:

| Config key | Default | Description |
| --- | --- | --- |
| `sc-subspace-max-pairs` | `1000` | Maximum number of key/value pairs a `/subspace` scan may return. |
| `sc-subspace-max-bytes` | `4194304` (4 MiB) | Maximum key+value bytes a `/subspace` scan may accumulate. |
| `sc-subspace-query-max-inflight` | `2` | Maximum concurrent `/subspace` queries. Only nodes with SS enabled serve `/subspace`, so this limit applies only to them. |

```toml
[state-commit]
sc-subspace-max-pairs = 1000
sc-subspace-max-bytes = 4194304
sc-subspace-query-max-inflight = 2
```

Both counters have a `db` attribute. Its value is the name of the data directory, so you can tell the FlatKV data DBs, the state store, and the receipt store apart. Turn the counters on per store in `app.toml`:

| Config key | Section | Store |
| --- | --- | --- |
| `enable-read-write-metrics` | `[state-commit.flatkv]` | FlatKV data DBs |
| `ss-enable-read-write-metrics` | `[state-store]` | State store, when `ss-backend = "pebbledb"` |
| `enable-read-write-metrics` | `[receipt-store]` | Pebble-based receipt store |

<Note>
The `[receipt-store]` `enable-read-write-metrics` key is no longer written into the generated `app.toml` template. The config reader still honors `receipt-store.enable-read-write-metrics` if you add it to `app.toml` by hand, but a newly generated file no longer renders it under `[receipt-store]`.
</Note>

```toml
[state-commit.flatkv]
enable-read-write-metrics = true
```


## State proof metrics

ABCI `/store` state proofs are deprecated and disabled by default (#4573). When a node receives a proof query (`prove=true` on a `/store` path that would produce a proof), it rejects the request with an `ErrNotSupported` error (`state proofs are disabled on this node; set state-commit.sc-enable-state-proof = true to enable`) and increments the `state_proof_rejected` counter. This affects light clients, which always set `prove=true`, and any ABCI client that sends `prove=true`. The proof code is scheduled for removal in a later release.

| Metric | Type | Description |
| --- | --- | --- |
| `state_proof_rejected` | Counter | Number of ABCI `/store` state proof queries rejected because proofs are disabled. Labeled by `store` (the store the query targeted) and `latest` (a boolean indicating whether the query was at the latest height). |

Operators who need to keep serving state proofs (for example, to support light clients) must opt in by setting `sc-enable-state-proof = true` in the `[state-commit]` section of `app.toml`:

| Config key | Default | Description |
| --- | --- | --- |
| `sc-enable-state-proof` | `false` | Enables deprecated ABCI `/store` state proofs. When `false`, proof queries are rejected with `ErrNotSupported`. This option will be removed with the proof code in a later release. |

```toml
[state-commit]
sc-enable-state-proof = true
```


## Log query parallelism for the littidx receipt store

The littidx receipt store is no longer selectable from the standard `[receipt-store]` backend config; `rs-backend` now only accepts `pebble`. The littidx code path (and its block-parallel `eth_getLogs` scanning) is used by the giga/evmonly path through the gigareceipt package rather than by a config-selected littidx backend.

Where the littidx-based receipt store is in use, each `eth_getLogs` query scans several blocks at the same time, and results stay in block and transaction order. `log-filter-parallelism` under `[receipt-store]` sets how many blocks one query scans at once. The default is `16`, and a value of `0` or less uses the default. The setting has no effect on the `pebble` receipt store backend.

```toml
[receipt-store]
log-filter-parallelism = 16
```

## Per-block hash logger

The state-commit store writes a CSV file of named hashes for each block. Each row has the memIAVL module and root hashes and the FlatKV DB and root hashes. It also has the app hash, the block hash, the results hash (the next block's `LastResultsHash`), and the changeset hash. To find where two nodes diverged, compare their logs with [`seidb hashlog compare`](/node/technical-reference#inspecting-hash-log-archives).

The hash logger is on by default. It writes to `data/hash.log` under the state-commit directory, which is `<home>/data/hash.log` by default. With the default settings, it keeps up to 16 GiB of closed log files. Configure it in the `[state-commit]` section of `app.toml`:

| Config key | Default | Description |
| --- | --- | --- |
| `sc-hash-logger-enable` | `true` | Turns the hash logger on or off. |
| `sc-hash-logger-directory` | empty | Directory for the log files. Empty means `data/hash.log` under the state-commit directory. |
| `sc-hash-logger-blocks-to-retain` | `0` | Number of recent blocks to keep. `0` turns off the block limit. |
| `sc-hash-logger-target-file-size` | `16777216` (16 MiB) | Size in bytes at which the logger closes a file and starts a new one. `0` uses the default. |
| `sc-hash-logger-max-disk-size` | `17179869184` (16 GiB) | Maximum total size in bytes of closed log files. `0` turns off the size limit. |

If you set both `sc-hash-logger-blocks-to-retain` and `sc-hash-logger-max-disk-size` to `0`, the logs grow without limit. To turn the hash logger off:

```toml
[state-commit]
sc-hash-logger-enable = false
```

## evmonly-loadtest Prometheus metrics

The `evmonly-loadtest` tool serves Prometheus metrics through an OpenTelemetry Prometheus exporter, so the counters it publishes arrive alongside the phase timers of the storage stack it drives (giga, FlatKV, and the view cache). It listens on port `9698` rather than the `9090` the sims use. Add a scrape target for it:

```yaml
scrape_configs:
  - job_name: 'evmonly-loadtest'
    static_configs:
      - targets: ['host.docker.internal:9698']
    scrape_interval: 5s
```

### Phase-timer metrics

The run is instrumented with two phase timers, each a counter of seconds spent in a labeled phase. Together with the storage stack's own instruments they account for the whole of a block's cost.

| Metric | Type | Description |
| --- | --- | --- |
| `evmonly_block_phase_duration_seconds_total` | Counter | Wall time of the single executor goroutine, broken into the phases of a store-backed block (`waiting_for_block`, `open_view`, `execute`, `occ_speculate`, `occ_validate`, `occ_merge`, `await_commit`, `encode_changesets`, `encode_receipts`, `write_receipts`, and `commit_state`), carried on a `phase` label. The slices sum to elapsed time. |
| `evmonly_pipeline_phase_duration_seconds_total` | Counter | Work across the goroutines of the stages that run ahead of the executor: `build_block` (constructing and signing a block's transactions), `recover_senders` (sender recovery during block preparation), and `waiting` (blocked rather than working). This is total work across workers, not wall time, and is what the executor's `waiting_for_block` is waiting on. |

### Pipeline metrics

The commit of a block runs behind the next block's execution, so a block pays the handoff (`commit_state`) plus whatever the previous commit had not finished (`await_commit`) rather than the write itself. `await_commit` near zero means the overlap is working.

| Metric | Type | Description |
| --- | --- | --- |
| `evmonly_loadtest_reorder_pending_blocks` | Gauge | Blocks built ahead of the next height in a streaming run (`--blocks=0`), held in the reorder buffer until that height is sent. Bounded by twice `--builders`; pinned near that bound means one builder is holding the rest back. |

### Grafana dashboard

The tool ships an `EVMOnly Loadtest` Grafana dashboard (`docker/monitornode/dashboards/evmonly-loadtest-dashboard.json`, uid `evmonly-loadtest`). It breaks down where a block's serial time goes and which stage of the pipeline is the constraint, with rows for block time, pipeline stages, state reads, commit, and runtime.



## Giga EVM-only executor OCC OpenTelemetry metrics

The Giga EVM-only executor emits optimistic concurrency control (OCC) metrics through the process-wide OpenTelemetry `MeterProvider`, so you can watch parallel-execution behavior without reading `BlockResult`. The executor emits one sample per block. The node binds the meter provider with a `sei_chain` Prometheus namespace, so each name below is scraped with that prefix (for example, `giga_occ_blocks_total` is scraped as `sei_chain_giga_occ_blocks_total`).

### Available OCC metrics

| Metric | Type | Description |
| --- | --- | --- |
| `giga_occ_blocks_total` | Counter | One sample per block, labeled by `outcome`. `parallel` and `fallback` are blocks that tried optimistic execution, `sequential` are blocks that had transactions but were ineligible (a single transaction, `OCCWorkers <= 1`, or registered custom precompiles), and `empty` are blocks with no transactions. Splitting the ineligible blocks from the empty ones keeps `parallel / (parallel + fallback + sequential)` a statement about OCC rather than about block rate. |
| `giga_occ_fallbacks_total` | Counter | Blocks that abandoned the optimistic path and re-ran sequentially, labeled by `reason`. |
| `giga_occ_reruns_total` | Counter | Transaction reruns scheduled by optimistic execution validation across the whole block. |
| `giga_occ_conflicts_total` | Counter | State access conflicts observed while validating optimistic execution, labeled by `access` and `kind`. |
| `giga_occ_rerun_depth` | Histogram | The deepest incarnation any single transaction reached (`MaxIncarnation`) per optimistically executed block, bucketed one per reachable incarnation. The histogram records every block that tried optimistic execution, including those that never reran a transaction. |

### Labels

| Label | Metric | Values |
| --- | --- | --- |
| `outcome` | `giga_occ_blocks_total` | `parallel`, `fallback`, `sequential`, or `empty`. |
| `reason` | `giga_occ_fallbacks_total` | The fallback reason, such as a validation conflict, a gas limit or gas overflow, max-incarnation exhaustion, or a closed OCC worker pool. |
| `access` | `giga_occ_conflicts_total` | `read` or `write`. |
| `kind` | `giga_occ_conflicts_total` | The conflicting state kind: `account`, `balance`, `nonce`, `code`, or `storage`. |

Every label vocabulary is closed: an `outcome`, `reason`, `access`, or `kind` value the emitter does not recognize collapses to `unknown` rather than adding a new series. Conflict addresses and storage slots are deliberately not labels, because they are per-contract and per-slot and would make the series unbounded; they remain available in `OCCStats.ConflictSamples` for logs and spans. A block's conflict samples are summed onto the access-by-kind series before being emitted, so the telemetry work per block is bounded by the label space rather than by the number of conflicting state keys.

### Attributes

| Attribute | Description |
| --- | --- |
| `table` | The table that the observation applies to. Present on per-table metrics such as `litt_bytes_read`, `litt_read_latency_seconds`, `litt_table_size_bytes`, and the flush/GC latency histograms. |
| `cache` | The cache instance that the observation applies to (`chunk_read` or `chunk_write`). Present on the `litt_chunk_cache_*` metrics, which distinguish read and write caches by this attribute instead of by separate metric names. |

### Migrating from legacy LittDB metrics

The OpenTelemetry migration changed the metric names, units, and shape. You must update your existing Prometheus and Grafana dashboards:

- Latency metrics moved from millisecond summaries (for example, `{namespace}_read_latency_ms`) to second histograms (`litt_read_latency_seconds`). Change thresholds and panel formatting from milliseconds to seconds.
- Counters and gauges gained a fixed `litt_` prefix and explicit units. For example, `bytes_read` became `litt_bytes_read`, and the cache weight gauge became `litt_chunk_cache_weight_bytes`.
- The per-cache series that previously had separate metric names (for example, `chunk_read_cache_*` and `chunk_write_cache_*`) are now the shared `litt_chunk_cache_*` metrics. The `cache` attribute distinguishes them.
- The `MetricsNamespace` and `MetricsRegistry` config fields no longer exist. Metric names are fixed, and the global OTel provider always backs the metrics. Set the scrape port with `MetricsPort`.

## Performance testing

<Accordion title="Example benchmark script using `eth_getLogs`">

```js
import { ethers } from 'ethers';

// Configuration
const EVM_RPC_URL = 'http://localhost:8545'; // EVM RPC endpoint to test
const CONTRACT_ADDRESS = '0x0000000000000000000000000000000000001002'; // replace with very active contract for best results
const INITIAL_BLOCK_RANGE = 50; // range of blocks to query using 'eth_getLogs'
const RANGE_INCREMENT = 10; // additional blocks to query each consecutive round
const MAX_TESTS = 50; // total number of rounds for testing

// Store metrics for final analysis
const metrics = [];

function getResponseSize(logs) {
  return Buffer.byteLength(JSON.stringify(logs), 'utf8');
}

function formatBytes(bytes) {
  if (bytes === 0) return '0 B';
  const k = 1024;
  const sizes = ['B', 'KB', 'MB', 'GB'];
  const i = Math.floor(Math.log(bytes) / Math.log(k));
  return `${parseFloat((bytes / Math.pow(k, i)).toFixed(2))} ${sizes[i]}`;
}

function padString(str, length) {
  return String(str).padEnd(length);
}

function analyzeResults(metrics) {
  console.log('\nPerformance Analysis');
  console.log('='.repeat(50));

  // Filter out queries with no logs for meaningful statistics
  const queriesWithLogs = metrics.filter((m) => m.logsCount > 0);
  const totalQueries = metrics.length;

  console.log(`\nGeneral Statistics:`);
  console.log(`Total Queries Run: ${totalQueries}`);
  console.log(`Queries with Logs: ${queriesWithLogs.length}`);
  console.log(`Empty Responses: ${totalQueries - queriesWithLogs.length}`);

  if (queriesWithLogs.length > 0) {
    const avgResponseTime = queriesWithLogs.reduce((acc, m) => acc + m.responseTime, 0) / queriesWithLogs.length;
    const avgLogsPerQuery = queriesWithLogs.reduce((acc, m) => acc + m.logsCount, 0) / queriesWithLogs.length;
    const maxLogs = Math.max(...queriesWithLogs.map((m) => m.logsCount));
    const maxLogsQuery = queriesWithLogs.find((m) => m.logsCount === maxLogs);

    console.log(`\nPerformance Metrics:`);
    console.log(`Average Response Time (with logs): ${avgResponseTime.toFixed(2)}ms`);
    console.log(`Average Logs per Query: ${avgLogsPerQuery.toFixed(2)}`);
    console.log(`Maximum Logs in Single Query: ${maxLogs}`);
    if (maxLogsQuery) {
      console.log(`- At Range Size: ${maxLogsQuery.rangeSize} blocks`);
      console.log(`- Response Time: ${maxLogsQuery.responseTime}ms`);
      console.log(`- Efficiency: ${maxLogsQuery.logsPerMs.toFixed(3)} logs/ms`);
    }

    // Identify optimal range size based on logs/ms
    const bestEfficiency = queriesWithLogs.reduce((best, m) => (m.logsPerMs > best.logsPerMs ? m : best));
    console.log(`\nOptimal Performance:`);
    console.log(`Best Efficiency: ${bestEfficiency.logsPerMs.toFixed(3)} logs/ms`);
    console.log(`- At Range Size: ${bestEfficiency.rangeSize} blocks`);
    console.log(`- Retrieved ${bestEfficiency.logsCount} logs in ${bestEfficiency.responseTime}ms`);
  }
}

async function testEthGetLogs() {
  const provider = new ethers.JsonRpcProvider(EVM_RPC_URL);

  try {
    const latestBlock = await provider.getBlockNumber();
    console.log(`Latest block: ${latestBlock} (0x${latestBlock.toString(16)})`);

    let currentToBlock = latestBlock;
    let currentRange = INITIAL_BLOCK_RANGE;
    let testCount = 0;

    // Column headers with fixed widths
    console.log('\nBlock Range         Time  Logs    Size     B/ms   Logs/ms  KB/Log  Range');
    console.log('='.repeat(80));

    while (testCount < MAX_TESTS && currentToBlock > 0) {
      const fromBlock = Math.max(0, currentToBlock - currentRange);

      try {
        const startTime = Date.now();
        const filter = {
          fromBlock: fromBlock,
          toBlock: currentToBlock,
          address: CONTRACT_ADDRESS
        };

        const logs = await provider.getLogs(filter);

        const endTime = Date.now();
        const responseTime = endTime - startTime;
        const logsCount = logs.length;
        const responseSize = getResponseSize(logs);

        // Calculate metrics
        const bytesPerMs = (responseSize / responseTime).toFixed(1);
        const logsPerMs = (logsCount / responseTime).toFixed(3);
        const kbPerLog = logsCount > 0 ? (responseSize / 1024 / logsCount).toFixed(2) : 'N/A';

        // Store metrics for analysis
        metrics.push({
          rangeSize: currentRange,
          responseTime,
          logsCount,
          responseSize,
          bytesPerMs: parseFloat(bytesPerMs),
          logsPerMs: parseFloat(logsPerMs),
          kbPerLog: kbPerLog !== 'N/A' ? parseFloat(kbPerLog) : 0
        });

        // Format block range
        const rangeDisplay = `${fromBlock.toString(16)}-${currentToBlock.toString(16)}`;

        // Log with fixed column widths
        console.log(padString(rangeDisplay, 17) + padString(responseTime, 6) + padString(logsCount, 8) + padString(formatBytes(responseSize), 9) + padString(bytesPerMs, 8) + padString(logsPerMs, 9) + padString(kbPerLog, 8) + currentRange);

        if (logsCount === 10000) {
          console.log(`\nWarning: Hit 10000 log limit at range ${currentRange}`);
        }

        currentToBlock = fromBlock - 1;
        currentRange += RANGE_INCREMENT;
        testCount++;
      } catch (error) {
        console.log(`Error at range ${currentRange}: ${error.message}`);
        currentRange = Math.max(INITIAL_BLOCK_RANGE, currentRange - RANGE_INCREMENT);
        currentToBlock = fromBlock - 1;
        testCount++;
      }

      await new Promise((resolve) => setTimeout(resolve, 1000));
    }

    // Perform final analysis
    analyzeResults(metrics);
  } catch (error) {
    console.error('Failed to initialize or get latest block:', error);
    process.exit(1);
  }
}
```
